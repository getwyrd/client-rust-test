═══ orphaned-lock-resolution ═══
An orphaned lock: a lock on a SECONDARY key whose PRIMARY was never written.
The primary carries no lock and no write record, so a reader cannot learn the
transaction's fate from it and MUST escalate to rollback_if_not_exist once the TTL
expires.

client-go does: the read succeeds, and its async resolver then clears the lock.
client-rust did not until tikv/client-rust#561 (pin 3408d95): check_txn_status matched
only Error::ExtractedErrors, but the plan shape (retry_multi_region -> merge ->
extract_error) could only deliver Error::MultipleKeyErrors, so the rollback_if_not_exist
heal path was dead code -- the read failed, the lock stayed, and the key was left
unreadable AND unwritable forever (#543). That showed as a divergence on `native.type`
(MultipleKeyErrors vs client-go's untyped error), visible only because the observation
keeps each client's own taxonomy alongside the canonical class. Ledger G-0001 is now
FIXED and asserts the two clients AGREE on every compared field.

BOTH RUNS SHARE ONE SETUP: client-go manufactures the orphan in both, using
CommitterProbe (exported from a NON-test file). Only the READER changes. So any
divergence below is attributable to the reader alone -- a strictly stronger claim than
gate::d6 can make, since d6 must manufacture the orphan through the public API with a
region split and a racing transaction, and therefore cannot tell 'I failed to BUILD the
orphan' apart from 'the client failed to RESOLVE it'.

═══ raw-checksum ═══
THE FIRST CAPABILITY CLAIM: raw Checksum exists in client-go and not in client-rust.

client-go serves rawkv.Checksum -- a SERVER-side crc64 over a key range
(kvrpcpb.RawChecksumRequest), returning crc64_xor / total_kvs / total_bytes. client-rust
has no such request type anywhere in its plan layer (rules doc RAW-4; roadmap 5.6). Its
driver answers `unsupported`, which is a first-class, comparable observation -- the
driver must NOT emulate the feature (a client-side scan-and-hash would checksum
different bytes under different semantics and manufacture agreement out of a
workaround).

So the claim surface is the CLASS: oracle `ok`, subject `unsupported`. The oracle's
checksum numbers ride along in the trace as evidence only -- crc64_xor and total_bytes
cover the key bytes, run prefix included, so they legitimately differ between the two
runs of this comparison and are never projected.

BOTH RUNS SHARE ONE SETUP: client-go writes the same three raw pairs in both; only the
CHECKER changes. Raw and transactional data are kept apart by construction (every key
lives under this run's unique prefix; no scenario mixes raw and txn ops on the same
keys; scenarios run serially) -- the APIVersion V1 caveat in kvrpcpb is about exactly
that mixing.

When client-rust gains raw checksum, this diff vanishes, ledger-check fires XCONVERGE,
and G-0002 is re-stated as an `expect = "agrees"` regression guard -- the designed
lifecycle for a closed gap.
