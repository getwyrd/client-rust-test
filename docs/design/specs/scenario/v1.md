# Spec: scenario -- v1

> Normative specification. **Status: DRAFT (unstable -- will change).** This
> document uses [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) keywords:
> MUST, SHOULD, MAY.

## 1. Motivation

A scenario is the one file both clients are driven through. It is written once and run with
its roles bound to different drivers, and the runner diffs what the two runs observed. The
format is declarative on purpose: **no conditionals, no loops, no variables, no expression
language.** A test that needs control flow is a Rust test, not a scenario.

## 2. Scope

Covered: the file `scenarios/<name>.json`, its fields, and the checks made when it is
loaded. The commands a step may carry are [parity-protocol/v1](../parity-protocol/v1.md)
§4.3; what a run observes and how two runs are compared is
[observation/v1](../observation/v1.md); how a scenario is tied to a gap is
[ledger/v1](../ledger/v1.md).

## 3. Conventions

A *plain name* matches `[a-z0-9][a-z0-9-]*`. An *executing role* is a role named by at
least one step whose op is not `sleep`.

## 4. Requirements

### 4.1 File

| field | type | required | meaning |
|---|---|---|---|
| `schema` | string | yes | `"parity-scenario/v1"` |
| `name` | string | yes | a plain name, equal to the file name without `.json` |
| `doc` | string | yes | what the scenario proves and why it is shaped this way |
| `gap` | string | yes | the ledger id this scenario is evidence for |
| `roles` | string[] | yes | the role names |
| `runs` | object[] | yes | each `{name, bind}`, `bind` mapping every role to `"rust"` or `"go"` |
| `compare` | string[2] | yes | the two run names to diff, oracle first |
| `also_compare` | string[] | no | opt-in projection paths ([observation/v1](../observation/v1.md) §4.5) |
| `steps` | object[] | yes | the steps, in order |

1. A scenario MUST NOT carry a field this table does not name.
2. `name` and every run name MUST be plain names: they become file names under `results/`.
3. `name` MUST equal the file's base name, and no two scenarios may share a name.

### 4.2 Runs and comparison

1. Run names MUST be unique.
2. Every run MUST bind every declared role, and MUST NOT bind a role that is not declared.
3. `compare` MUST name two different runs, both defined.
4. The two compared runs MUST bind at least one executing role to different drivers.
   Otherwise the comparison contrasts nothing and an `agrees` claim would pass without the
   subject ever running.
5. At least one step MUST execute a command.

### 4.3 Steps

| field | required | meaning |
|---|---|---|
| `id` | yes | unique within the scenario; ledger claims refer to steps by id, never by position |
| `role` | yes, except for `sleep` | a declared role |
| `cmd` | yes | a command ([parity-protocol/v1](../parity-protocol/v1.md) §4.3), or `{"op":"sleep","ms":N}` |
| `assert` | no | a precondition: `lock_count` (exact number of locks) and/or `class` (a class tag) |
| `why` | for `sleep`, yes; otherwise no | why the step exists |

1. A step MUST NOT carry a field this table does not name, and `cmd` MUST NOT carry a field
   its op does not define.
2. `sleep` is the runner's own op: it waits on the cluster's clock and talks to no driver.
   It MUST carry a non-negative integer `ms` and a `why`.
3. A step MUST NOT use `hello`.
4. Every `b64` argument MUST be canonical base64.
5. `scan_locks` MUST carry `batch_size` > 0.
6. An `assert` is a harness precondition, never a parity claim. When it fails, the run is
   inadmissible ([observation/v1](../observation/v1.md) §4.3).

### 4.4 When the checks run

Every requirement in §4.1 to §4.3 that concerns one file MUST be checked when the scenario
is loaded, before any driver starts. A scenario that fails one MUST NOT run. `parity-runner
--check <file>...` performs exactly these checks and runs nothing.

The checks that span files (§4.1.3, and the ledger rules in [ledger/v1](../ledger/v1.md) §4.4)
are made by `scripts/spec-check.sh`.

## 5. Versioning and compatibility

Adding an optional field is a change to this version only if the runner already rejects it
today (§4.1.1); otherwise it is `parity-scenario/v2`. Removing or renaming a field, or
loosening a check, requires v2.

## 6. Conformance

- `cargo test -p parity-runner`: one test per check in §4.
- `make spec-check`: every file in `scenarios/` passes `parity-runner --check` and the
  cross-file checks.
