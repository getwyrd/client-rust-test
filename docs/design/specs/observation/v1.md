# Spec: observation, projection and diff -- v1

> Normative specification. **Status: DRAFT (unstable -- will change).** This
> document uses [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) keywords:
> MUST, SHOULD, MAY.

## 1. Motivation

Two clients in two languages answer the same command. To compare them honestly the harness
needs a shared vocabulary for what happened, and a fixed rule for which parts of an answer
are compared. The rule is: **canonicalize the question, never the evidence.** Drivers record
everything; the projection decides what a comparison looks at. A projection can be widened
later; evidence thrown away at capture is gone.

## 2. Scope

Covered: the observation a driver returns for each command, the canonical classes, the
projection that reduces a trace to comparable fields, the diff, and the trace file.
The commands themselves are [parity-protocol/v1](../parity-protocol/v1.md). What a
divergence means for a gap is [ledger/v1](../ledger/v1.md).

## 3. Conventions

- *Observation*: one command's result (`crates/parity-proto/src/observation.rs`).
- *Class*: the canonical result vocabulary (`class.rs`). Its tag is the `snake_case` name.
- *Projection*: a map from step id to `path → string` (`project.rs`).
- *Run prefix*: the unique key prefix of one run ([parity-protocol/v1](../parity-protocol/v1.md) §4.4).

## 4. Requirements

### 4.1 Layers

An observation has three layers, each compared differently:

| layer | content | compared by default |
|---|---|---|
| `class` | the closed canonical vocabulary, from the kvproto TiKV sent | always |
| `proto` | the `kvrpcpb` message as JSON, `{container: {message: payload}}` | presence and message type only |
| `native` | the client's own error: `lang`, `type`, `display`, verbatim | never; always kept and printed |

1. A driver MAY normalize presentation: the same fact spelled in its language's idiom
   (Go's `ErrNotExist` and Rust's `Ok(None)` are both `not_found`).
2. A driver MUST NOT normalize fact. A failure that one client shows and the other does not
   MUST NOT be retried, mapped to another class, or otherwise smoothed over.
3. A driver MUST keep `native` for every error it maps.

### 4.2 Classes

The class set is closed: `ok`, `not_found`, `write_conflict`, `key_exists`,
`txn_not_found`, `unresolved_lock`, `deadlock`, `assertion_failed`, `retryable`,
`aborted`, `commit_ts_too_large`, `lock_wait_timeout`, `undetermined`, `region_error`,
`pd_error`, `rpc_error`, `mixed` (with `parts`), `unsupported` (with `detail`),
`driver_error` (with `detail`), `internal` (with `detail`).

1. Adding a class is a reviewed change to `class.rs` and both drivers' mapping tables.
2. An error a driver has no explicit mapping for MUST become `internal`, never another
   class.
3. A multi-key error whose members all report the same class MUST collapse to that class,
   with the member count in `error_count`. Members that disagree MUST become `mixed`.
4. `unsupported` means the client lacks the capability. It is a real, comparable answer and
   is admissible.

### 4.3 Admissibility

1. An observation of class `internal`, `driver_error` or `region_error`, or a `mixed` with
   any such part, makes its whole run inadmissible: the run is evidence of nothing, and
   MUST NOT be reported as a divergence.
2. `region_error` means the cluster moved, so the runner MAY retry the run. It retries at
   most 3 attempts in all, then reports the run inadmissible.
3. A failed step `assert` (a scenario precondition, [scenario/v1](../scenario/v1.md) §4.3)
   makes the run inadmissible in the same way.

### 4.4 Other observation fields

| field | content |
|---|---|
| `value` | bytes read, as `{b64, utf8?}`; `utf8` is a reader's echo, set only when the bytes are printable UTF-8 |
| `locks` | `scan_locks` results: `key`, `primary`, `kind` (kvrpcpb `Op` by name), `ttl_ms`, `txn_start_ts` |
| `start_ts`, `commit_ts` | transaction timestamps |
| `error_count` | per-key errors surfaced, when several |
| `checksum` | `crc64_xor`, `total_kvs`, `total_bytes` from `raw_checksum`; evidence only |

Only `b64` is ever compared for bytes; `utf8` MUST NOT affect a verdict.

### 4.5 Projection

Default paths, for every step:

| path | value |
|---|---|
| `class` | the class tag |
| `unsupported.detail` | the detail, when the class is `unsupported` |
| `class.parts` | the part tags of a `mixed`, sorted, comma-joined |
| `value` | the bytes with the run prefix replaced by `{P}`, as UTF-8 if valid, else base64; `<absent>` if none |
| `locks.count` | the number of locks |
| `locks` | each lock as `key=… primary=… kind=… ttl=zero\|positive`, prefix redacted, sorted, joined by ` \| ` |
| `commit_ts` | `<ts>` if present, `<absent>` otherwise |
| `proto.present` | `true` or `false` |
| `proto.type` | `container.message`, exactly two levels, when present |

Opt-in paths, added only when the scenario lists them in `also_compare`:

| path | value |
|---|---|
| `native.type` | the client's own error type |
| `proto` | the whole proto, as JSON |
| `errors.count` | `error_count`, or `<absent>` |

1. The run prefix MUST be redacted on bytes, before any UTF-8 decision.
2. Timestamps, TTL values, `native.display`, `checksum` and `start_ts` MUST NOT be
   projected.
3. An unknown `also_compare` path MUST fail when the scenario is loaded.

### 4.6 Diff

1. The diff compares two projections step by step and path by path, over the union of
   both sides' step ids and paths. A path missing on one side reads `<step absent>`.
2. Each difference is a divergence `{step, path, oracle, subject}`, where `oracle` is the
   first run in the scenario's `compare` and `subject` the second.
3. Divergences are compared as a set; their order carries no meaning.

### 4.7 Artifacts

The runner writes, under `results/`:

- `traces/<scenario>.<run>.json`: schema `parity-trace/v1`, with `scenario`, `run`,
  `provenance` (the provenance stamp as it stood when the run happened,
  [provenance/v1](../provenance/v1.md)), `roles` (each role's driver and `hello`), `prefix`,
  and `steps` (`id`, `role`, `op`, `observation`), unedited;
- `divergence.<scenario>.json`: schema `parity-divergence/v1`, with `scenario`, `gap`,
  `provenance`, `oracle`, `subject` (the two run names) and `divergences`.

## 5. Versioning and compatibility

Adding an opt-in path or an observation field that defaults to absent is compatible.
Adding a default path, changing what a path projects, or adding a class changes the result
of existing claims. Such a change MUST come with a re-run of every ledger claim, and is
recorded in this document's next version.

## 6. Conformance

`cargo test -p parity-proto` covers admissibility, base64 strictness, prefix redaction,
lock ordering and the opt-in path check. `make ledger` exercises the whole chain against a
real cluster.
