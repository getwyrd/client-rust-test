# Spec: provenance and admissibility -- v1

> Normative specification. **Status: DRAFT (unstable -- will change).** This
> document uses [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) keywords:
> MUST, SHOULD, MAY.

## 1. Motivation

Cargo cannot pin a path dependency, so a build never says which client-rust it exercised.
A result is evidence only if it records the world it was produced in (both clients, the
cluster, the toolchains and the harness itself), and only if that world is the pinned one.
This document says what is recorded, and when a result may settle the ledger or judge a
change.

## 2. Scope

Covered: `results/provenance.json` (written by `scripts/provenance.sh`), the three modes,
the admissibility rules `scripts/ledger-check.sh` applies, and
`results/candidate-verdict.json`. What is pinned is `pins.toml` (§4.5). The verdicts are
[ledger/v1](../ledger/v1.md) §4.5.

## 3. Conventions

- *Pin*: a value in `pins.toml`. *On pin*: equal to it.
- *Digest*: the output of `scripts/tree-digest.py` over a tree: a content hash of every
  tracked and untracked, not ignored, file. Symlinks are refused.
- *Base*: the harness commit `git merge-base HEAD origin/main`.

## 4. Requirements

### 4.1 The stamp

`provenance.sh` MUST write `results/provenance.json` before any scenario runs, with schema
`parity-provenance/v1` and:

| section | fields |
|---|---|
| top | `captured_at`, `strict` (bool), `mode` (`strict` \| `candidate` \| `advisory`) |
| `client_rust` | `path`, `rev`, `branch`, `describe`, `dirty`, `pinned_rev`, `matches_pin` |
| `client_go` | `module`, `version`, `pinned_version`, `replaced`, `verified`, `matches_pin` |
| `cluster` | `pd_addr`, `pinned_version`, `pinned_pd_image`, `pinned_tikv_image`, `observed_pd_version`, `observed_tikv_versions`, `verified`, `matches_pin` |
| `toolchain` | `rust`, `pinned_rust`, `rust_matches_pin`, `go`, `pinned_go`, `go_matches_pin` |
| `harness` | `rev`, `dirty` |
| `candidate` | candidate mode only: `client_rust.{contains_pin, digest}`, `harness.{base, digest}` |

1. The runner MUST copy the stamp, as it stood when the run happened, into every trace and
   divergence file it writes. Admissibility is judged from that copy, never from a stamp
   re-read later.
2. `client_go.version` and `replaced` come from the Go module graph; each trace's Go
   `hello` reports them again from inside the binary that ran
   ([parity-protocol/v1](../parity-protocol/v1.md) §4.2).

### 4.2 Modes

`PARITY_MODE` selects the mode; `PARITY_STRICT=1` means `strict`, and contradicting it is an
error. With neither set, the mode is `advisory`.

| mode | client-rust | harness | oracle, cluster, toolchains | what the result may do |
|---|---|---|---|---|
| `strict` | on pin and clean | committed, and the same commit that judges it | on pin | settle the ledger |
| `candidate` | contains the pin; fixed by digest | fixed by digest, on a base | on pin | judge one change (§4.3) |
| `advisory` | anything | anything | anything | nothing: a diff to read |

1. `provenance.sh` in strict or candidate mode MUST stop before any scenario runs when the
   world is off pin.
2. `ledger-check` MUST refuse to settle the ledger from any result whose stamp is not
   strict, and MUST refuse a strict result when any of these holds:
   - client-rust off pin, dirty, or produced against a pin that has since moved;
   - the harness dirty, or a different commit from the one running `ledger-check`;
   - client-go `replaced`, off pin, or reported off pin by any trace's Go `hello`;
   - the Go toolchain off pin;
   - the cluster unidentified or off pin.
3. A result missing a stamp, or with an unknown stamp schema, MUST be refused.

### 4.3 Candidate mode

`PARITY_MODE=candidate PARITY_GAP=<id>` judges one change (a loop bundle) against the
pinned world.

1. `PARITY_GAP` MUST name an entry in `ledger.toml`. Only the default `pins.toml` and
   `ledger.toml` are accepted.
2. The change MUST NOT edit `pins.toml`, add an entry other than `<id>`, remove an entry,
   edit any other entry, or edit any other entry's scenario, all compared with the base.
3. Each result's `candidate.harness.base` MUST equal the base, and both digests MUST equal
   the digests of the trees as they are when `ledger-check` runs. client-rust MUST contain
   the pin, and the Rust toolchain that ran MUST be on pin.
4. The oracle, cluster and Go toolchain checks of strict mode apply unchanged.
5. `ledger-check` MUST delete any earlier `results/candidate-verdict.json` before its first
   check. It MUST write a new one only once every admissibility check has passed, and
   then writes it whether or not the claims hold:

   | field | value |
   |---|---|
   | `schema` | `"parity-candidate-verdict/v1"` |
   | `gap` | `<id>` |
   | `outcome` | the declared gap's verdict ([ledger/v1](../ledger/v1.md) §4.5), reported, not judged |
   | `others_hold` | true when every other claim holds |
   | `others` | every other gap's verdict |
   | `declared_entry` | `new` \| `changed` \| `unchanged`, compared with the base |
   | `harness_changed_files` | every file that differs from the base |
   | `provenance` | the declared gap's `candidate` stamp |

6. `ledger-check` exits 0 only when the declared gap has a result and every other claim
   holds. A candidate run MUST NOT print the "every claim holds" line: it is not evidence
   for the ledger.

### 4.4 Advisory runs

An advisory run MAY be used for reading a diff, for example CI's upstream view at
`upstream_base`. `ledger-check` MUST refuse it in both strict and candidate mode.

### 4.5 pins.toml

| table | keys |
|---|---|
| top | `schema = "parity-pins/v1"` |
| `[client_rust]` | `upstream`, `fork` (URLs), `branch`, `rev` (40 hex), `upstream_base` (40 hex) |
| `[client_go]` | `module`, `version` (a Go version or pseudo-version), `rev` (40 hex) |
| `[cluster]` | `tikv_version` (`vX.Y.Z`), `pd_image`, `tikv_image` (`repo:tag@sha256:<64 hex>`) |
| `[cluster.versions."vX.Y.Z"]` | `pd_image`, `tikv_image`, as above; zero or more |
| `[toolchain]` | `rust` (`X.Y.Z`), `go` (`X.Y.Z`) |

1. `pins.toml` MUST NOT carry a table or key this table does not name.
2. No other file may name a revision, module version or image. `make pins-check`
   (`scripts/check-pins.sh`) checks that every consumer agrees with `pins.toml`; `make
   spec-check` checks the shape above.

## 5. Versioning and compatibility

A new stamp field is compatible when `ledger-check` does not need it. A new admissibility
rule is a change to v1. Accepting a result that v1 refuses requires
`parity-provenance/v2`.

## 6. Conformance

- `scripts/tests/test_candidate_mode.py`: every refusal in §4.3, against fixtures built
  from a real run.
- `make spec-check`: §4.5.
- CI runs `make provenance` and `make ledger` in strict mode on every PR.
