# Spec: parity protocol -- v1

> Normative specification. **Status: DRAFT (unstable -- will change).** This
> document uses [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) keywords:
> MUST, SHOULD, MAY.

## 1. Motivation

The runner (`crates/parity-runner`) drives two clients written in two languages through
the same scenario. It does so by talking to one driver process per role over a small
command protocol. The Rust half of the protocol is `crates/parity-proto`; the Go half is
hand-written in `go/driver`. Nothing but this document and the `hello` handshake keeps the
two halves in step, so the contract is written down here.

## 2. Scope

Covered: the framing, the handshake, the command set, the response shape, and how the
protocol may change. The content of an observation is [observation/v1](../observation/v1.md);
the scenario file that names the commands is [scenario/v1](../scenario/v1.md).

Not covered: how a driver maps its client's errors (each driver owns its own mapping
table), and the trace file the runner writes (observation/v1 §6).

## 3. Conventions

- *Runner*: `parity-runner`. *Driver*: a process that executes commands against one
  client: `parity-driver-rust` (tikv-client, the subject) or `parity-driver-go`
  (client-go, the oracle).
- The protocol identifier is the string `parity-cmd/v1` (`PROTOCOL_VERSION` in
  `crates/parity-proto/src/command.rs`). This document is its specification.
- JSON field and value names are `snake_case`.

## 4. Requirements

### 4.1 Transport and framing

1. The runner MUST start one driver process per role of a run, never one per language
   (client-go's configuration is a process global).
2. The runner writes commands to the driver's stdin and reads responses from its stdout.
   Each message MUST be exactly one JSON object followed by `\n` (NDJSON). A message MUST
   NOT contain a raw newline.
3. The exchange is strictly request then response, one at a time. A driver MUST write
   exactly one response line for every command line it reads, and MUST NOT write anything
   else to stdout. Logs go to stderr; a driver MUST redirect anything a library might print
   to stdout.
4. The runner MAY start a driver through a wrapper (`PARITY_DRIVER_WRAPPER=<program>`,
   started as `<program> <driver-binary>`). The wrapper MUST relay stdin and stdout
   unchanged.

### 4.2 Handshake

1. The first command MUST be `{"op":"hello"}`. A driver MUST answer it with
   `{"hello": {...}}`:

   | field | type | meaning |
   |---|---|---|
   | `driver` | string | `"rust"` or `"go"` |
   | `protocol` | string | the protocol identifier the driver implements |
   | `client.name` | string | `"tikv-client"` or `"github.com/tikv/client-go/v2"` |
   | `client.version` | string | the version actually linked, as the binary itself reports it |
   | `client.replaced` | bool | Go only: the module was `replace`d by a local tree |
   | `features` | string[] | capabilities the driver has, e.g. `prewrite_only` |
   | `config` | string[] | every deviation from a stock client, e.g. `drop_check=warn` |

2. The runner MUST refuse to continue when `protocol` differs from its own identifier.
3. `client.version` MUST come from the binary (Go: `runtime/debug.ReadBuildInfo()`), never
   from a file the version is later checked against.
4. `hello` is the runner's own handshake. A scenario step MUST NOT use it.

### 4.3 Commands

A command is a JSON object whose `op` field names it. Byte strings are `KeyArg`s:
`{"s": "<utf-8 text>"}` or `{"b64": "<canonical base64>"}`.

| op | fields | meaning |
|---|---|---|
| `open_client` | `name` | open a transactional client against `$PD_ADDRS` |
| `close_client` | `name` | close it |
| `open_raw_client` | `name` | open a raw-mode client |
| `begin` | `session`, `client`, `mode` (`optimistic` \| `pessimistic`) | begin a transaction |
| `put` | `session`, `key`, `value` | buffer a write |
| `get` | `session`, `key` | read inside the transaction |
| `commit` | `session` | commit |
| `rollback` | `session` | roll back |
| `abandon` | `session` | drop the transaction without commit or rollback |
| `snapshot_get` | `client`, `key` | read at the current timestamp, outside any transaction |
| `scan_locks` | `client`, `start`, `end`, `batch_size` | every lock in `[start, end)` |
| `prewrite_only` | `session`, `primary`, `keys` | prewrite the given keys and stop |
| `raw_put` | `client`, `key`, `value` | raw, non-transactional put |
| `raw_checksum` | `client`, `start`, `end` | server-side checksum of a raw range |

1. A driver MUST answer every command except `hello` with `{"observation": {...}}`
   ([observation/v1](../observation/v1.md)).
2. A driver MUST NOT emulate a capability its client lacks. It MUST answer
   `{"class":"unsupported","detail":"..."}` instead.
3. `scan_locks` MUST return every lock in the range. `batch_size` is a paging hint, never a
   limit; each driver pages as its client requires.
4. A command the driver cannot parse, or one naming an unknown session or client, MUST be
   answered with `class: driver_error`, never with any other class.
5. The Rust driver MUST begin transactions with `drop_check(CheckLevel::Warn)` (the default
   panics on drop, which would make `abandon` impossible) and MUST report it in
   `hello.config`.

### 4.4 Key namespacing

The runner, not the driver, places every key under the run's unique prefix before sending
a command (`KeyArg::as_key`):

1. text containing `{P}`: the token is replaced by the prefix;
2. text without `{P}`: the prefix is prepended;
3. base64: the prefix bytes are prepended.

Values are namespaced by `as_value`: `{P}` in text is replaced, base64 is passed through
unchanged. A driver MUST use the bytes it receives as they are.

## 5. Versioning and compatibility

1. Changes within `parity-cmd/v1` MUST be additive: a new op, or a new optional field with
   a default. Renaming or removing an op or field, or changing a field's meaning, requires
   `parity-cmd/v2` and a new version of this document.
2. A new op MUST be implemented by both drivers in the same change. A driver whose client
   lacks the capability implements the op by answering `unsupported` (§4.3.2).
3. A scenario naming an op the runner does not know MUST fail when the scenario is loaded,
   before any driver starts ([scenario/v1](../scenario/v1.md) §4.4).

## 6. Conformance

- `cargo test -p parity-proto`: every command round-trips as one NDJSON line; key
  namespacing cannot be escaped.
- `parity-runner --check <scenario>...`: loads and validates scenarios without running
  them (used by `scripts/spec-check.sh`).
- The handshake check in `crates/parity-runner/src/driver.rs` refuses a protocol mismatch
  at every run.

## 7. Open questions

- Nothing yet checks that the Go driver's command structs and `command.rs` agree field by
  field. A mismatch shows up only as a `driver_error` at run time.
