# Spec: parity ledger -- v1

> Normative specification. **Status: DRAFT (unstable -- will change).** This
> document uses [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) keywords:
> MUST, SHOULD, MAY.

## 1. Motivation

`ledger.toml` is the verdict of this repository: every known difference between client-rust
(the subject) and client-go (the oracle), each with a declared expectation that a pinned run
must confirm field by field. A wrong outcome is a hard failure in both directions, so the
file cannot rot into "these are red forever" without someone noticing.

## 2. Scope

Covered: the file's fields, the verdicts `scripts/ledger-check.sh` computes from it, and the
rules that tie an entry to its scenario. How a run is made admissible is
[provenance/v1](../provenance/v1.md); what a divergence is, is
[observation/v1](../observation/v1.md) §4.6.

## 3. Conventions

- *Entry*: one `[[gap]]` table. *Claim*: what an entry declares about its scenario's diff.
- *Repo path*: a path relative to the repository root.

## 4. Requirements

### 4.1 File

1. The top level MUST hold `schema = "parity-ledger/v1"` and `[[gap]]` tables, and nothing
   else.
2. The ledger MUST declare at least one entry.

### 4.2 Entry fields

| field | required | value |
|---|---|---|
| `id` | yes | `G-` followed by four digits; unique |
| `slug` | yes | a plain name (`[a-z0-9][a-z0-9-]*`) |
| `kind` | yes | `behavioral` \| `capability` \| `performance` |
| `area` | yes | dotted lowercase, e.g. `txn.lock-resolution` |
| `status` | yes | `OPEN` \| `FIXED` |
| `title` | yes | one line |
| `expectation` | yes | prose: what client-go does and what client-rust must do |
| `scenario` | yes | repo path of the scenario that is this entry's evidence |
| `expect` | yes | `diverges` \| `agrees` |
| `divergence` | when `expect = "diverges"` | one or more `{step, path, oracle, subject}` |
| `upstream_issue` | no | URL of the upstream issue |
| `upstream_pr` | no | URL of the upstream fix |
| `finding` | no | repo path of the write-up under `findings/` |
| `roadmap` | no | repo path, optionally followed by a space and a section, e.g. `docs/parity-roadmap.md §5.6` |
| `rules` | no | repo path, optionally followed by a space and a rule id, e.g. `docs/design/specs/client-rules/v1.md RAW-4` |
| `oracle_wrong` | reserved | see §4.6 |

1. An entry MUST NOT carry a field this table does not name.
2. `status = "OPEN"` MUST go with `expect = "diverges"`, and `status = "FIXED"` with
   `expect = "agrees"`.
3. An `agrees` entry MUST NOT carry `divergence`.
4. Every repo path an entry names MUST be relative, MUST stay inside the repository, and
   MUST exist.

### 4.3 Kinds

- `behavioral`: both clients do the operation, and they behave differently.
- `capability`: client-go has the operation and client-rust does not. The subject answers
  `unsupported`; the driver never emulates it.
- `performance`: reserved for the performance tier. No runner produces a performance
  divergence in v1.

### 4.4 Entry and scenario

1. Each entry's `scenario` MUST be written `scenarios/<file>.json`, name an existing file,
   and that file's `gap` field MUST equal the entry's `id`.
2. Every file under `scenarios/` MUST be named by exactly one entry.
3. Each `divergence.step` MUST be a step id of that scenario.
4. Each `divergence.path` MUST be a default projection path, or an opt-in path the scenario
   lists in `also_compare` ([observation/v1](../observation/v1.md) §4.5).

### 4.5 Verdicts

`ledger-check` runs every scenario's divergence set against its entry. Divergences are
compared as a set of `(step, path, oracle, subject)`.

| `expect` | observed | verdict | in strict mode |
|---|---|---|---|
| `agrees` | no divergence | **HOLDS** | pass |
| `agrees` | any divergence | **NEW GAP** | hard fail: declare it or fix it |
| `diverges` | exactly the declared set | **XDIVERGE** | pass: the gap is still open |
| `diverges` | no divergence | **XCONVERGE** | hard fail: the gap closed, so the pin, README and entry are stale |
| `diverges` | any other set | **WRONG DIVERGENCE** | hard fail: the run is evidence of nothing |
| either | no result file | **MISSING** | hard fail |

1. A claim holds when it comes out HOLDS or XDIVERGE.
2. When a gap closes (XCONVERGE), the entry MUST be kept and flipped to `status = "FIXED"`,
   `expect = "agrees"`, so it guards against a regression. An entry MUST NOT be deleted
   because its gap closed.
3. In candidate mode ([provenance/v1](../provenance/v1.md) §4.3) the declared gap's
   verdict is reported, not judged, and every other claim must hold.

### 4.6 ORACLE-WRONG (reserved)

Sometimes the subject diverges because client-go is the one that is wrong. Only a human may
declare that, and the declaration goes in the entry:

```toml
oracle_wrong = { declared_by = "<name>", date = "YYYY-MM-DD", evidence = "<URL or repo path>" }
```

An entry carrying it, whose scenario diverges exactly as declared, gets the verdict
**XORACLE**: it holds, and it never counts as a regression of client-rust. The upstream
client-go report is the `evidence`.

`ledger-check` does not implement XORACLE yet. Until it does, an entry MUST NOT carry
`oracle_wrong`, and `spec-check` rejects one that does.

## 5. Versioning and compatibility

A new optional field, a new kind or a new status is a change to v1 only together with the
checks for it in `spec-check`. Changing what a verdict means, or removing a field, requires
`parity-ledger/v2`.

## 6. Conformance

- `make spec-check` checks §4.1 to §4.4 and the reservation in §4.6 without a cluster.
- `make ledger` computes §4.5 against a pinned run.

## 7. Open questions
